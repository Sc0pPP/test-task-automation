# Продажи по артикулам за день

Скрипт читает выгрузку заказов `sales.csv` и строит отчёт `daily_by_sku.csv`: одна строка на пару «артикул × день».

| Колонка | Что в ней |
|---|---|
| `sku` | артикул |
| `order_date` | день, ГГГГ-ММ-ДД |
| `orders` | число заказов за день, включая отменённые |
| `revenue` | выручка, сумма `quantity × price` только по выкупленным (`delivered`) заказам |

Строки отсортированы по `sku`, затем по дате. Каждый заказ учитывается один раз.

## Как запустить

Нужен Python 3.8 или новее. Внешних зависимостей нет, ничего устанавливать не надо.

1. Положите выгрузку в корень репозитория под именем `sales.csv`.
2. Запустите:

   ```bash
   python3 daily_by_sku.py
   ```

3. Результат появится в `daily_by_sku.csv` рядом со скриптом. В консоль выводится число уникальных заказов и строк отчёта.

Пути можно передать явно: `python3 daily_by_sku.py путь/к/sales.csv путь/к/результату.csv`.

В репозитории уже лежит готовый `daily_by_sku.csv`, посчитанный по выданной выгрузке.

## Как проверял, что расчёт верный

**1. Контрольные суммы по всему файлу** — скрипт `check_report.py`:

```bash
python3 check_report.py
```

Он заново считает итоги прямо из `sales.csv`, не используя код основного скрипта, и другим способом: дубли убирает как полностью одинаковые строки, а не по `order_id`. Затем сверяет с суммами по отчёту:

| Показатель | Значение |
|---|---|
| Строк в выгрузке | 13 858 |
| Удалено дублей | 60 |
| Заказов всего (сумма `orders`) | 13 798 |
| Выручка всего (сумма `revenue`) | 10 276 540 ₽ |
| Строк в отчёте | 631 (12 артикулов, 56 дней с 17.08 по 11.10.2026) |

Также проверяется, что пары «артикул + дата» не повторяются и отчёт отсортирован. Все проверки проходят.

**2. Ручная сверка одной строки** через `awk`, без Python: UYT-0001 за 2026-08-17 — 28 заказов, 27 650 ₽, как в отчёте.

```bash
sort -u sales.csv | awk -F, '$3=="UYT-0001" && $2=="2026-08-17" {n++; s=tolower($6); gsub(/ /,"",s); if (s=="delivered") r+=$4*$5} END {print n, r}'
```

**3. Юнит-тесты** на маленьком наборе, где результат посчитан руками: дубль заказа, опечатки в статусах, пустое количество у отменённого заказа, конфликтующий дубль.

```bash
python3 -m unittest -v
```

## Проблемы в данных и что с ними сделал

| Проблема | Сколько | Решение |
|---|---|---|
| Полные дубли строк | 60 | Заказ учитывается один раз по `order_id`. Все дубли полностью совпадают с оригиналом. Если встретится тот же `order_id` с другими данными — скрипт остановится с ошибкой, а не выберет строку наугад |
| Статусы с разным регистром и пробелами: `Delivered`, `DELIVERED`, `delivered `, `Cancelled`, `CANCELLED` | 32 | Привожу к нижнему регистру и убираю пробелы |
| Опечатка `canceled` вместо `cancelled` | 3 | Считаю отменой |
| Пустой `quantity` | 4 | Все четыре заказа отменены, на выручку не влияют. В `orders` учитываются, как и любой отменённый заказ |

Если в данных появится незнакомый статус (например, `returned`), скрипт упадёт с ошибкой и назовёт значение — лучше остановиться, чем молча посчитать неверно. Если пустой `quantity` встретится у выкупленного заказа, скрипт тоже упадёт: выручку по такому заказу посчитать нельзя.

Остальное проверил и проблем не нашёл: все даты корректные, артикулы одного формата, у каждого артикула одна цена на весь период, в каждой строке 6 полей.

## Что не доделано и в чём не уверен

- **Дни без заказов в отчёт не попадают.** Если по артикулу в какой-то день не было заказов, строки с нулями нет. В условии об этом не сказано; если нужна полная сетка дней, это легко добавить.
- **Дубль определяю по `order_id`.** Исхожу из того, что в одном заказе один артикул, — в этой выгрузке так и есть. Если в заказе может быть несколько артикулов, ключ дубля нужно расширить до `order_id + sku`.
- **`canceled` считаю отменой** — это самое правдоподобное прочтение, но формально это предположение.
